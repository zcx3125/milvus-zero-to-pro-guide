# 第一章：先理解 Milvus，再开始敲命令

[返回教程首页](../README.md) · [下一章：安装与连接](02-installation.md)

> 阅读目标：不用先学线性代数，也能解释“为什么要向量检索、Milvus 保存什么、一次搜索经历哪些步骤”。
> 本教程主线为 Milvus `v3.0.1` 与 PyMilvus `3.0.1`。版本核对日期为 2026-09-14。概念图是本教程绘制的示意图，不是官方产品截图。

## 1. 先想象一家公司的资料越来越多

假设你在一家公司的 IT 部门工作，有这些资料：

- 《员工密码修改指南》
- 《忘记登录口令怎么办》
- 《账号被锁定后的处理方法》
- 《打印机无法连接排查手册》
- 《VPN 连接操作说明》

员工输入：“我进不了公司系统，密码想不起来了。”

人很容易判断：第二份资料很可能有用。
但如果程序只查找这句话的完整文字，可能一份都找不到。
因为资料里写的是“忘记登录口令”，员工说的是“密码想不起来”。

这就是语义检索要解决的一类问题：用词不一样，但意思接近。

## 2. 关键词搜索和语义搜索有什么区别

### 2.1 关键词搜索：根据词语是否匹配寻找资料

例如搜索“打印机”，系统寻找含有“打印机”的资料。
常见实现会分词、统计词频，使用 BM25 等方法排序。
它不一定要求逐字完全相同，也可以做同义词扩展、拼写处理和字段加权。

关键词搜索尤其适合：

- 产品型号，例如 `ABC-1234`。
- 错误码，例如 `ERR_AUTH_401`。
- 人名、编号、专有术语。
- 用户明确知道自己要找的关键词。

所以“关键词检索已经过时”是错误的。
企业搜索经常把关键词检索与向量检索一起使用。

### 2.2 语义搜索：先把含义转换为数字，再找相似数字

一个能处理文本的 Embedding 模型会把句子转换为一串数字。
这串数字就是向量。

模型希望：含义相近的文本，在向量空间中也比较接近。
于是，“忘记登录口令”和“密码想不起来”有机会被匹配到一起。

但这是模型学到的近似关系，不是必然正确的事实。
模型可能不懂某个行业术语，也可能把“允许退款”和“不允许退款”判断得过于相近。
因此，真正的业务系统需要评测，不能只看几个演示问题就判断效果。

## 3. 向量到底是什么

### 3.1 先从三个数字理解

为了方便教学，假设我们人为定义三个属性：

1. 与账号问题的关系。
2. 与网络问题的关系。
3. 与硬件问题的关系。

那么，可以人为给三份资料打分：

```text
忘记密码指南： [0.95, 0.10, 0.05]
VPN 连接指南：[0.15, 0.95, 0.10]
打印机维修：   [0.05, 0.20, 0.95]

用户问题：     [0.90, 0.15, 0.05]
```

用户问题与“忘记密码指南”的数字比较接近。
计算机可以用数学公式比较它们，不需要人工逐篇阅读。

这里的三个数字组成了一个三维向量。
“维度”指的是向量里有多少个分量，也就是这里的三个位置。

### 3.2 真实模型不是人工设定的三个属性

真实 Embedding 模型可能输出几百维或几千维的向量。
例如，一个模型配置输出 384 维，就会产生 384 个数字。

这些维度通常不能分别解释为“账号”“网络”“硬件”等人类语义标签。
上面的三维例子只是帮助理解距离的教学道具，不能用于真实语义搜索。

把一段文字随便转成随机数、字符编码或哈希值，也不能获得可靠的语义相似性。
真正有用的是模型训练后学到的向量表示。

### 3.3 维度不是越大越好

更高维度通常意味着更多存储、更大计算量和更多网络传输。
检索效果还取决于模型训练数据、语言能力、行业适配和文本切分。

选择维度时应该遵循所用模型的能力和推荐配置，然后在自己的问题集上评测。
不能只因为“1024 大于 384”就断定前者更适合你的业务。

## 4. Embedding 模型、Milvus、大语言模型分别干什么

这是最容易混淆的一组概念。

### 4.1 Embedding 模型：负责把内容转换成向量

它的输入可以是文本；支持多模态的模型也可能处理图片等内容。
它的输出是向量，不是面向用户的一段回答。

例如：

```text
输入：员工忘记密码后，可在自助服务门户重置。
输出：[0.023, -0.187, 0.614, ...]
```

在本教程基础流程里，Python 程序先调用 Embedding 模型，再把向量写入 Milvus。
Milvus 某些功能可以结合内置函数或外部模型服务完成特定处理，但不能因此假设“只要装上数据库，就能自动理解任何资料”。

### 4.2 Milvus：负责保存、组织和检索向量及相关字段

它可以保存向量，也可以保存主键、文本、分类、日期、JSON 等业务相关数据。
例如，一条记录可以同时包含原文、来源路径、租户 ID 和向量。

Milvus 并不是“只能存数字，不能存文字”。
不过，它的核心定位是向量数据管理与检索，不是替代所有业务数据库。
订单支付、复杂多表事务等业务，仍应根据需求使用关系型数据库等合适系统。

### 4.3 大语言模型：负责根据问题和资料组织回答

检索完成后，你可以把找到的资料和用户问题交给大语言模型。
模型据此生成解释，并附上资料引用。

Milvus 本身不会替你证明资料一定正确，也不会自动保证回答没有幻觉。
应用需要规定：资料不足时承认不知道，回答中保留来源，必要时交给人工处理。

## 5. Milvus 是什么，适合解决哪些问题

Milvus 是开源向量数据库。
它帮助应用对大量向量进行相似性搜索，并结合普通字段进行过滤。
SDK 是程序访问数据库的工具包；本教程使用的 Python SDK 叫 PyMilvus。

常见应用有：

- 企业知识库：按问题寻找相关制度、手册和 FAQ。
- 以图搜图：把图片变成向量，查找相似图片。
- 相似案例检索：寻找相关工单、法律案例或技术故障。
- 商品发现：按描述寻找语义相关商品。
- 推荐与内容去重：把向量检索作为候选召回环节。

这些应用的最终效果不只取决于 Milvus。
图片向量不准确，换一个数据库也不会自动修复图片理解能力。

### 5.1 什么情况下不必立刻引入 Milvus

如果只有几十条固定问答，普通文件或小型数据库可能足够。
如果业务主要是精确查订单号，普通数据库索引更直接。
如果团队已经重度使用 PostgreSQL，也可以先评估 pgvector，减少系统数量。

选型要考虑数据规模、并发、过滤条件、运维能力和已有系统。
“用了向量数据库”本身不是项目价值，解决了实际检索问题才是。

## 6. 从文件夹和表格理解 Milvus 的数据结构

下面的类比用于建立直觉，不代表它与关系型数据库行为完全相同。

### 6.1 Database：数据库，类似项目空间

一个 Milvus 实例可以组织不同的 Database。
你可以把它想成不同项目的数据空间。
入门代码没有指定数据库时，一般使用默认的 `default`。

Database 是组织和管理数据的一层边界，不能单凭命名就认为实现了全部租户安全隔离。
安全边界还需要鉴权、角色权限、服务端校验和正确的部署方式。

### 6.2 Collection：集合，类似一张用途明确的表

例如创建 `company_knowledge` 集合，保存公司知识库的文档片段。
一个集合可以有多个标量字段以及符合版本能力的向量字段。

不要为每一篇文档都创建一个集合。
同一业务中格式相同的数据，通常先放进同一个集合，再用 `document_id` 等字段区分。

### 6.3 Schema：模式，说明记录应该长什么样

Schema 声明字段名称、类型、向量维度、主键等约束。
例如，我们规划一条文档片段记录包含：

```text
id          ：整数主键
document_id ：原始文档标识
chunk_id    ：片段编号
text        ：片段原文
source      ：资料出处
tenant_id   ：所属企业或租户
vector      ：固定维度的浮点向量
```

显式定义 Schema 可以早点发现数据格式错误。
动态字段适合某些灵活属性，但初学时不宜靠动态字段掩盖混乱的数据设计。

### 6.4 Entity：实体，也就是一条记录

例如“一份员工手册的第 3 个片段”可以是一条 Entity。
不一定一整份 PDF 对应一条记录。
长文档通常会拆分成多个片段，每个片段分别生成向量。

### 6.5 Primary key：主键，记录的身份标识

主键帮助你查询、更新或删除指定记录。
常见选择是 `INT64` 整数，或符合配置的 `VARCHAR` 字符串。
你可以自己分配主键，也可以使用自动生成的 ID。

如果应用需要重复导入同一批资料，需要提前设计幂等策略。
“幂等”通俗地说就是：同一操作多执行一次，不应意外生成第二份业务数据。
不要假设 `insert()` 会像带唯一约束的 SQL 表那样替你拒绝所有重复主键写入；更新语义应按文档使用 `upsert()` 等接口，并由应用维护稳定 ID。

### 6.6 Vector field：向量字段

这里存放 Embedding 的结果。
例如 Schema 中声明 `dim=384`，每次写入和检索的该字段就必须提供 384 个数字。

维度相同还不够。
两种不同模型即使都输出 384 维，也可能处在完全不同的向量空间，不能随意混用。
文档与问题应使用同一模型体系以及相互兼容的编码方式。
某些模型要求文档与问题分别带不同前缀，应遵循该模型说明。

### 6.7 Scalar field：标量字段，普通业务属性

这里的“标量”可以先理解为向量之外的普通字段。
例如分类、价格、部门、是否公开、文档 ID。

你可以先限制 `department == "IT"`，再在允许的数据里搜索相似内容。
这样就不会把行政制度和技术故障手册混在一起检索。
更完整的字段类型以对应版本 Schema 文档为准。

### 6.8 Partition：分区，集合中的逻辑分组

分区可以帮助组织集合中的数据，并在合适的查询方式下缩小搜索范围。
但“每个用户建立一个分区”并不一定是好设计，分区数量和管理成本都要考虑。
还可以研究 Partition Key 等功能，具体限制要看部署模式与版本。

注意两个不同概念：这里的集合分区不是 IVF 索引内部聚类形成的“桶”。
不要把它们当成一回事。

### 6.9 Index：索引，为快速检索建立的辅助结构

如果每次查询都计算与所有记录的距离，数据大时成本很高。
索引可以帮助系统减少需要检查的候选。
部分方法会用少量准确性换取速度，因此需要评测召回率。

索引不是原始数据的替代品，也不是备份。
更详细的索引选择与参数解释在[第四章](04-indexes-and-production.md)。

### 6.10 Load / Release：加载 / 释放查询资源

创建集合、写入数据，不代表所有查询资源已经就绪。
加载集合是让查询节点准备好提供搜索服务。
入门可以把它理解为“把需要查询的数据和索引准备到可服务状态”。

实际数据驻留方式可能受索引、缓存、mmap 等配置影响，不必把 Load 理解成“一次性把所有数据完整复制进内存”。
`release_collection()` 用于释放查询资源；它不等于删除持久化数据。
`drop_collection()` 则会删除集合，操作前要确认目标。

## 7. 一次完整搜索经历什么

### 7.1 建库阶段：对资料做准备

1. 读取文档，提取正文。
2. 清理重复页眉、无意义空行等噪声。
3. 把长文档切成适合检索的片段。
4. 用 Embedding 模型生成每个片段的向量。
5. 把向量、原文、来源和权限字段写入 Milvus。
6. 按需求建立索引并准备查询资源。

### 7.2 查询阶段：把问题变成候选资料

1. 应用先确认访问者身份和可查询范围。
2. 用兼容的 Embedding 模型把问题变成向量。
3. 把问题向量、过滤条件和 `top_k` 发给 Milvus。
4. Milvus 返回最接近的若干记录及其分数。
5. 应用展示资料，或者继续做重排序和回答生成。

`top_k=5` 表示最多取排名靠前的 5 条候选，不是“答案有 5 分把握”。
如果只有 3 条记录满足过滤条件，结果可能少于 5 条。
如果所有资料都不相关，最近的几条仍可能不相关，所以还需要拒答与质量检查。

## 8. 四种常见使用方式

### 8.1 Milvus Lite：适合轻量学习和本地原型

Lite 让应用以更轻量的方式在本地使用 Milvus 能力，通常通过本地数据库文件连接。
它适合验证流程、运行小型样例和开发原型。

Lite 不是完整分布式集群。
支持的索引、分区、权限和其他功能可能与服务端不同。
Python 版本、操作系统和安装包支持范围也需要单独核对；Windows 用户不要直接假设所有 Lite 包都能原生安装。

本教程主线选择 Docker 中的 Standalone，避免把 Lite 的行为当成所有部署模式的行为。

### 8.2 Milvus Standalone：适合学习、开发及适当规模负载

Standalone 把主要 Milvus 服务组件放在单个进程中运行。
它仍可能依赖独立的 etcd 和对象存储容器。
所以“Standalone”不等于“整个系统永远只有一个容器”。

它适合开始学习，但一台电脑上的 Compose 演示不具备完整的生产高可用能力。
是否能承载正式业务，要根据性能、可靠性要求和资源实测决定。

### 8.3 Milvus Distributed / Cluster：用于需要独立扩缩容的场景

集群模式把组件分开部署，以便分别扩展写入、查询等能力。
常见部署基础是 Kubernetes。

收益是灵活扩缩容，代价是更多服务、监控、资源规划和故障处理工作。
不能看到“企业级”三个字，就认为每个毕业项目都应该从 Kubernetes 集群开始。

官方说明中，Standalone 不能直接在线升级成集群。
迁移应作为独立的数据迁移项目，先验证目标版本和数据导入方式。

### 8.4 Zilliz Cloud：托管服务

Zilliz Cloud 是基于 Milvus 技术的商业托管服务。
你通常连接一个云端 Endpoint，而不是自己维护 etcd、对象存储和集群节点。

需要评估费用、区域、网络访问、数据合规以及与开源版本的功能差异。
托管服务减少基础设施维护工作，不会免除应用权限设计和数据质量管理。

## 9. 为什么安装时会看到 etcd、MinIO、Woodpecker

![Milvus 各组件的职责示意](../assets/images/02-deployment.png)

### 9.1 etcd：记住系统如何组织数据

可以把 etcd 理解成系统的“登记簿”。
它保存集合结构、组件协调等元数据。
元数据说明数据怎样组织，不是把所有原始向量都塞进 etcd。

如果登记簿丢了，仅仅保留一堆数据文件也不代表系统能正确恢复。
这就是生产备份不能只随便复制某个文件夹的原因之一。

### 9.2 MinIO / S3：持久保存较大的数据对象

对象存储用来保存数据文件、索引文件等大对象。
MinIO 提供兼容 S3 的对象存储接口，常见于本地安装演示。
正式环境也可能使用其他兼容对象存储或云服务，具体支持范围看部署文档。

对象存储不是用户直接修改 Milvus 记录的入口。
不要为了“清理空间”去手动删除它内部的对象。

### 9.3 Woodpecker：写入日志与恢复链路的一部分

WAL 是 Write-Ahead Log，即预写日志。
可以先把它理解为“先按顺序记下发生了哪些写入，方便协调处理和故障恢复”。

Woodpecker 是 Milvus 使用的 WAL 系统。
它可结合对象存储和元数据存储工作；在适用的嵌入式配置中，无需额外部署独立消息队列服务。

Milvus 不同版本与部署方案可能使用过不同日志后端。
看到旧文章中的 Pulsar、Kafka 或 RocksMQ，不要直接把配置复制到新版本。
本教程按固定版本的安装配置运行，并以该配置决定具体服务。

### 9.4 不必一开始就会手动管理全部组件

学习阶段，先知道各组件干什么，以及哪些目录和卷存放重要数据。
能启动、连接、检索、停止并保留数据后，再逐步学习备份和监控。
不要把学习 Milvus 变成先补完所有分布式系统课程。

## 10. Milvus 在 RAG 里处于哪一环

RAG 是 Retrieval-Augmented Generation，常译为检索增强生成。
意思是：回答之前先找资料，再让模型参考资料生成答案。

![文档入库与 RAG 问答的职责划分](../assets/images/04-rag.png)

可以用一句话理解各方分工：

- 文档处理程序负责“把资料整理好”。
- Embedding 模型负责“把内容变成可比较的向量”。
- Milvus 负责“找出相关候选资料”。
- Reranker 负责“更仔细地重新排序候选资料”。
- 大语言模型负责“根据提供的资料组织回答”。
- 应用程序负责“身份、权限、引用展示、审计和错误处理”。

Reranker 是重排序模型，不是每个入门项目都必须立刻加入。
但在业务对答案质量要求较高时，它常常值得评估。

检索到文档不等于有权使用文档。
权限条件必须进入可信服务端的检索流程，不能只在最终页面隐藏内容。
